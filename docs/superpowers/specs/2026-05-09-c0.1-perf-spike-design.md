# C0.1 — Performance Spike Design

- **Date:** 2026-05-09
- **Issue:** [#1](https://github.com/hanku4u/local-equs-client/issues/1)
- **Branch:** `c0.1-performance-spike`

## Goal

Validate the stack assumption that real parquet → DuckDB query with downsampling → PyQtGraph render is snappy enough for the 100-chart scenario. If it isn't, stop and reconsider the stack before C0.2.

## Targets

| Metric | Target |
| --- | --- |
| Initial render (8 charts × ~2000 points) | < 1.5 s |
| Zoom re-query | < 500 ms |
| Peak RSS | < 500 MB |

## Synthetic dataset

The plan's example (~30 sensors, 1 Hz, several days, ~100 MB) is the *baseline* case. We deliberately stress the stack near the upper end to surface scaling issues now:

- **5 simulated etch tools × 100 sensors each** = 500 sensor-streams
- **10 Hz** sampling
- **Sparse temporal layout** — tools only emit rows during active wafer processing

### Realistic wafer-processing schedule

Per tool:

- **8-hour operating window** (per-tool offset so tools aren't synchronized)
- Wafer run: ~90 s of dense 10 Hz data
- Inter-wafer gap: ~15 s (no rows)
- Lot = 25 wafers (~45 min wall-clock)
- Inter-lot gap: 5–15 min (no rows)
- Occasional 30–60 min maintenance gaps

This produces parquet that is **sparse temporally and dense spatially** — i.e., the actual shape of production etch-tool data (no padding/NaN during idle).

### Sensor catalog (100 per tool, same canonical names across tools)

| Group | Count | Examples |
| --- | --- | --- |
| OES wavelengths | 20 | `oes_350nm`, `oes_440nm`, … |
| MFC channels | 20 | `mfc_cf4_setpoint`, `mfc_cf4_actual`, `mfc_o2_*`, `mfc_ar_*`, … |
| RF | 10 | `rf_forward_power`, `rf_reflected_power`, `rf_match_position`, `rf_voltage_dc`, `rf_bias`, … |
| Substrate/chuck temps | 10 | `substrate_temp_zone1` … `zone10` |
| Chamber | 10 | `chamber_pressure`, `wall_temp`, `lid_temp`, … |
| ESC | 10 | `esc_voltage`, `esc_current`, `esc_temp`, … |
| He cooling | 10 | `he_pressure_inner`, `he_flow`, … |
| Misc | 10 | slit valve state, lift pin, turbo speed, … |

Per-sensor signal: sin + noise + step changes that simulate recipe steps within a wafer run. Each tool's noise seed is different so cross-tool comparison shows realistic variation.

### File layout

One parquet per tool: `spike/data/{tool_id}.parquet`.

We deliberately **skip the production hour-bucketed layout** (`{tool_id}/YYYY/MM/DD/HH.parquet`) — that's a M2 concern. For the spike, one file per tool keeps the generator simple and exercises DuckDB multi-file queries (5 files via `read_parquet([...])`).

Estimated total size: 150–200 MB compressed.

## Spike workflow (`spike/spike_render.py`)

1. If `spike/data/` is missing or empty, generate it (one-time, ~1–2 min).
2. Build a PySide6 main window with a PyQtGraph `GraphicsLayoutWidget`.
3. Pick **8 sensors spread across multiple tools** (mimics real cross-tool queries).
4. Time the initial render:
   - Per tool: DuckDB `read_parquet` + `time_bucket` aggregation → ~2000 buckets per chart → Arrow → numpy → plot.
   - All 8 charts get linked x-axes, mean line, min/max `FillBetweenItem` band.
5. Scroll-wheel zoom triggers re-query at finer resolution; time it.
6. Capture peak RSS via `psutil.Process().memory_info().rss` after first render and after zoom.
7. Write `spike/results.md` with timing, memory, environment, and a pass/fail verdict.

## Dependencies

Existing main deps already in `pyproject.toml`: `PySide6`, `pyqtgraph`, `duckdb`, `pyarrow`, `httpx`, `requests`.

New under `[project.optional-dependencies].spike`:

- `numpy` — array math for synthetic signal generation
- `psutil` — process memory measurement

## Files

- `spike/generate_data.py` — synthetic data generator (importable)
- `spike/spike_render.py` — main entry point
- `spike/data/{tool_id}.parquet` — generated, gitignored
- `spike/results.md` — auto-generated, gitignored

## Out of scope

- Query/result caching, LRU (M4)
- Viewport virtualization, progressive rendering (M4)
- View modes — overview/standard/focus (M4)
- Server/manifest endpoints (M2+)
- Hour-bucketed file partitioning (M2)
- Saved sets, mapping editor, time-range thumbnail (M1+)

## Decision criterion

If any target is missed:

> **Stop M0. Reconsider the stack before starting C0.2.** Don't wishfully proceed — the entire client architecture rides on these assumptions.
